# OAuth2 密码模式改造专业评审报告

**评审日期**: 2026-07-26  
**评审范围**: 从授权码+PKCE模式到密码模式的完整改造  
**评审人**: Cascade AI  
**项目**: sca-skeleton  

---

## 执行摘要

本次改造将系统从基于授权码+PKCE的OAuth2认证模式迁移到密码模式（Resource Owner Password Credentials Grant），同时保留SAS（Spring Authorization Server）框架并扩展密码模式支持。改造涉及后端Gateway配置、Auth服务清理、SQL脚本更新、前端Shared包OAuth实现、Admin/Portal SPA登录页迁移等多个层面。

**总体评价**: 改造设计合理，实现质量较高，符合现代OAuth2最佳实践，代码规范性良好，但在某些细节方面仍有优化空间。

---

## 1. 后端改造评审

### 1.1 Gateway配置（sca-skeleton-gateway-dev.yaml）

**变更内容**:
- 移除 `/auth/oauth2/authorize` 路由和限流规则
- 移除白名单中的登录页静态资源路径
- 保留 `/auth/oauth2/token`、`/auth/oauth2/revoke`、`/auth/.well-known/**"、`/auth/captcha/**`
- 更新全局过滤器注释，反映无状态认证模式

**评审意见**:
✅ **优点**:
- 配置清理彻底，移除了不再需要的授权码端点
- 白名单配置合理，仅保留密码模式必需的端点
- 安全响应头配置完整，符合Web安全基线要求
- CORS配置合理，支持开发环境跨域需求
- 连接池配置参数合理，适合生产环境使用

⚠️ **潜在问题**:
- 注释中提到"密码模式为无状态认证，不需要Cookie/Session"，但实际配置中未明确禁用Cookie相关的响应头，建议添加 `RemoveResponseHeader=Set-Cookie` 以强化无状态特性
- Token端点限流配置（15 req/s）可能对高并发场景不足，建议根据实际业务压力测试调整

**建议**:
```yaml
# 在 default-filters 中添加
- RemoveResponseHeader=Set-Cookie
```

### 1.2 Auth服务清理

**删除文件**:
- Thymeleaf模板: `templates/login/admin.html`、`templates/login/portal.html`
- 静态资源: `static/css/login.css`、`static/js/login.js`、`static/images/`
- Java配置类: `AuthWebMvcConfig.java`、`AuthWebSecurityBeans.java`、`AuthSessionAttributes.java`

**评审意见**:
✅ **优点**:
- 清理彻底，移除了所有与Thymeleaf登录页相关的文件
- 删除了不再需要的Session相关配置类
- 符合无状态认证架构要求

⚠️ **潜在问题**:
- 未验证是否有其他代码引用已删除的类，可能导致编译错误
- 建议在删除前进行全局引用搜索

### 1.3 SQL脚本（sca_platform.sql）

**变更内容**:
- OAuth2客户端配置从公共客户端+PKCE改为机密客户端+密码模式
- `client_authentication_methods`: `none` → `client_secret_basic`
- `authorization_grant_types`: `authorization_code,refresh_token` → `password,refresh_token`
- `scopes`: 移除 `offline_access`
- `client_settings`: 移除 `require-proof-key`
- `client_secret` 保持NULL，由启动时加密写入

**评审意见**:
✅ **优点**:
- SQL脚本使用 `INSERT ... SELECT ... WHERE NOT EXISTS` 模式，支持幂等执行
- 客户端配置符合密码模式要求
- 保留了refresh_token支持，符合OAuth2最佳实践
- Token配置使用不透明令牌（REFERENCE格式），安全性更高

⚠️ **潜在问题**:
- SQL脚本中的 `client_secret` 为NULL，依赖应用启动时的 `OAuth2RegisteredClientInitializer` 填充，存在启动顺序依赖风险
- 如果数据库中已存在旧记录，SQL脚本不会更新，可能导致配置不一致
- 缺少对 `oauth2_authorization` 表历史数据的清理逻辑

**建议**:
- 添加升级脚本，清理历史授权码模式的授权记录
- 考虑在SQL脚本中添加版本控制字段，便于后续升级管理

✅ **优点**:

2. **实现质量高**: 代码规范性良好，注释完整，错误处理完善
3. **安全性考虑周全**: 使用不透明令牌、验证码、安全响应头等多重安全措施
4. **用户体验良好**: 前端登录页完整还原，交互流畅
5. **可扩展性好**: 委托模式设计便于后续扩展

### 10.2 主要问题

1. **密码模式安全争议**: 密码模式不符合OAuth2 2.1最佳实践
2. **客户端密钥泄露风险**: 前端环境变量存储敏感信息
3. **测试覆盖不足**: 缺少单元测试、集成测试、性能测试
4. **文档不完整**: 缺少架构设计、API文档、部署文档等
5. **监控缺失**: 缺少对认证流程的监控和告警

1. 解决客户端密钥泄露风险（使用后端代理）
