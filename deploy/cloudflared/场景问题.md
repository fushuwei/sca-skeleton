# Cloudflared Tunnel 场景问题与解决方案

**服务器：** 192.168.1.105 (Ubuntu Server)
**域名：** newease.cloud **部署时间：** 2026-07-27

## 问题 1：cloudflared 启动失败 - network is unreachable

### 症状

启动 cloudflared 时出现错误：

```
ERR failed to run the datagram handler error="write udp [::]:55854->198.41.200.233:7844: sendmsg: network is unreachable"
```

### 根因

1. **GFW 封锁**：Cloudflare Tunnel 边缘节点（198.41.192.0/24 和 198.41.200.0/24，端口 7844）在国内被封锁
2. **HTTP_PROXY 环境变量无效**：cloudflared 不支持 HTTP_PROXY 环境变量
3. **proxychains4 无法建立连接**：代理服务器也被 GFW 限制

### 解决方案：tsocks + SOCKS5 透明代理

#### 1. 安装 tsocks

apt-get install -y tsocks

#### 2. 配置 /etc/tsocks.conf

server = 127.0.0.1 server_port = 7891 server_type = 5

# 本地网络不走代理

local = 192.168.0.0/255.255.0.0 local = 10.0.0.0/255.0.0.0 local = 172.16.0.0/255.240.0.0 local = 127.0.0.0/255.0.0.0

reuse = yes

#### 3. 确保 mihomo (Clash) 已启动

systemctl start mihomo systemctl status mihomo

#### 4. 测试连接

killall cloudflared 2>/dev/null tsocks cloudflared tunnel --edge-ip-version 4 run thinkpad-tunnel

#### 5. 配置 systemd 服务

创建 /etc/systemd/system/cloudflared.service.d/override.conf

启动服务：

systemctl daemon-reload systemctl enable --now cloudflared

## 问题 4：cloudflared 服务停止后无法自愈（Error 1033）

### 症状

- 访问 https://newease.cloud 出现 Cloudflare Error 1033（"This page is not available"）
- 服务器上 `systemctl status cloudflared` 显示 `inactive (dead)`，退出状态为 `status=0/SUCCESS`
- 必须手动 `systemctl restart cloudflared` 才能恢复

### 根因

systemd 默认的 `Restart=on-failure` 只在进程**异常退出**（非 0 退出码）时重启。但 cloudflared 在以下场景会**正常退出**（exit status=0）：

- mihomo 代理重启导致连接断开
- 网络抖动导致边缘连接丢失
- cloudflared 内部主动 graceful shutdown

`on-failure` 不处理 status=0 的退出，服务停止后无法自愈。

### 解决方案

修改 `/etc/systemd/system/cloudflared.service.d/override.conf`，在 `[Service]` 段添加：

```ini
Restart=always
RestartSec=30s
```

`Restart=always` 不区分退出码，任何退出都自动重启；`RestartSec=30s` 避免频繁重启导致 CPU 飙高。

```bash
systemctl daemon-reload
systemctl restart cloudflared
```

## 问题 5：访问 /admin 跳转到 http://newease.cloud:8080/admin/

### 症状

访问 https://newease.cloud/admin 时，浏览器地址栏跳转到 http://newease.cloud:8080/admin/，然后报 Cloudflare Error 1033 或连接超时。

### 根因

Nginx 配置中使用相对路径的重定向：

```nginx
location = /admin {
    return 301 /admin/;   # 相对路径
}
```

Nginx 对相对路径的 `return 301` 会自动拼接绝对 URL，规则是 `$scheme://$host:$server_port`。在本架构中：

- `$server_port = 8080`（Nginx 容器监听端口，cloudflared 回源到 8080）
- `$scheme = http`（cloudflared → Nginx 走 HTTP，HTTPS 在 Cloudflare 边缘终止）
- `$host = newease.cloud`（浏览器原始 Host 头透传）

拼出来的 `Location` 头是 `http://newease.cloud:8080/admin/`，导致：

1. **暴露内网端口**：浏览器地址栏出现 8080，攻击者可借此探测内网拓扑
2. **协议降级**：从 HTTPS 跳到 HTTP，浏览器/CDN 的 HSTS 策略拒绝执行
3. **Cloudflare Error 1033**：Cloudflare 边缘无法回源到 8080 端口（cloudflared 只代理 80/443）

### 解决方案

修改 `deploy/nginx/conf.d/sca-skeleton.conf`，用绝对 URL 显式指定协议和域名：

```nginx
location = /admin {
    return 301 https://$host/admin/;
}
```

`$host` 是浏览器原始 Host 头（`newease.cloud`），`https://` 绕开 `$scheme` 的 HTTP 默认值，不拼接 `$server_port`。

### 验证

```bash
curl -sI https://newease.cloud/admin
# 期望：location: https://newease.cloud/admin/
```

## 问题 6：portal 登录页 OPPO Sans 字体加载失败（图标显示异常）

### 症状

访问 https://newease.cloud 打开 portal 登录页时：

- body 文本字体回退到系统默认（与设计稿不一致，视觉效果差）
- 部分图标渲染异常（图标字符依赖字体加载）

### 根因

**Nginx 默认 `mime.types` 不包含 `.ttf` 扩展名映射**，导致 OPPO Sans 22MB TTF 字体被当作 `application/octet-stream` 返回。

配合 Nginx 配置中的安全响应头：

```nginx
add_header X-Content-Type-Options "nosniff" always;
```

浏览器拒绝加载 MIME 类型不匹配的资源，OPPO Sans 字体加载失败。

### 错误的认知：以为是 CSP 阻止 Google Fonts

最初怀疑是 CSP 阻止了 Material Symbols 图标字体从 Google CDN 加载，尝试修改 CSP 放开 `https://fonts.googleapis.com` 和 `https://fonts.gstatic.com`，**但这个方向是错的**：

- Material Icons / Material Symbols 字体通过 `@quasar/extras` 包**打包到本地 `/assets/*.woff2`**，不从 Google CDN 加载
- `font-src 'self' data:` 已经允许同源字体加载，CSP 不是问题
- `.woff2` 扩展名在 nginx mime.types 中已默认映射为 `font/woff2`，无需额外配置

真正的根因是 `/fonts/` 路径下的 `.ttf` 文件 MIME 类型缺失。

### 解决方案

在 `deploy/nginx/conf.d/sca-skeleton.conf` 新增 `/fonts/` location 块：

```nginx
location /fonts/ {
    root /usr/share/nginx/html/portal;
    default_type font/ttf;
    try_files $uri =404;
}
```

**为什么用 `default_type` 而不是 `types { }` 块：**

- `types { }` 会覆盖继承的 MIME 表，导致 `.woff2` 也被当作 `font/ttf` 返回（错误）
- `default_type` 只对未匹配到的扩展名生效，`.woff2` 仍走 nginx 默认的 `font/woff2` 映射

### 验证

```bash
curl -sI "http://localhost:8080/fonts/OPPO_Sans_4.0/OPPO%20Sans%204.0.ttf"
# 期望：Content-Type: font/ttf

curl -sI "http://localhost:8080/fonts/JetBrains_Mono/JetBrainsMono-Regular.woff2"
# 期望：Content-Type: font/woff2（不受影响）
```
